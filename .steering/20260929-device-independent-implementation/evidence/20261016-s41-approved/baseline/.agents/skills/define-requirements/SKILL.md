# Define Requirements

ユーザーのアイデアを出発点に、質問と回答の反復で曖昧さ・矛盾・未決事項・隠れた前提を減らす。main agentが対話と合意を担当し、`document_author`が合意した要件を`docs/ideas/`の仕様正本へ反映する。

## 入力

- ざっくりしたアイデア、または更新対象の`docs/ideas/*.md`を受け取る。
- 明示されたパスは、正規化後もリポジトリの`docs/ideas/`配下にあるMarkdownファイルだけを受け付ける。`docs/ideas/initial-requirements.md`は不存在でも新規作成対象として受け付ける。それ以外の明示パスは、実在する更新対象に限る。
- 初期要件テンプレートには[initial-requirements-template.md](assets/initial-requirements-template.md)、追加仕様テンプレートには[feature-spec-template.md](assets/feature-spec-template.md)を使う。
- 初期要件の状態は[initial-requirements-validation.md](references/initial-requirements-validation.md)で判定する。

## モード選択

`AGENTS.md`、`PROJECT_CONTEXT.md`、既存の対象仕様を読み、初期要件の`absent / present`と`missing / blank / valid`を共通判定基準で記録する。`valid`は必須6領域の充足を表し、対話の完了やユーザー合意を意味しない。

1. 初期要件が`missing`または`blank`なら **Initial Requirements Mode**。`docs/ideas/initial-requirements.md`を作成・補完する。追加仕様を依頼されても初期要件の不足を示し、追加仕様の作成・更新は開始しない。
2. `valid`でも、ユーザーが初期アプリ要件をまだ詰めている、または初期要件の変更を明示している場合は **Initial Requirements Mode**。合意した変更だけを既存ファイルへ反映する。セットアップ済みなら永続文書との影響関係も確認する。
3. 初期要件が固まり`valid`でも、次の永続6文書のいずれかが存在しなければ **中間状態**。不足パスを列挙し、「初期要件は完成しているが、永続設計文書がまだ作成されていない」と伝え、次の工程として`$setup-project`を案内して終了する。追加仕様の新規作成・更新へ進まない。
4. `valid`かつ永続6文書がすべて存在し、既存アプリの追加機能・変更または既存feature specの更新を相談している場合は **Feature Requirements Mode**。日付付き仕様を作成・更新する。
5. 初期要件の見直しか追加仕様か、または対象が曖昧なら、書き込み前に意図と対象を確認する。モード選択だけを理由に既存仕様を移動・改名しない。

永続6文書は`docs/product-requirements.md`、`docs/functional-design.md`、`docs/architecture.md`、`docs/repository-structure.md`、`docs/development-guidelines.md`、`docs/glossary.md`。Feature Requirements Modeではこれらと関連する`docs/ideas/`、必要ならコードの関連箇所を読み、既存仕様との整合性を確認する。文書が存在しても内容不足や矛盾があれば、存在だけで要件確定と扱わない。

## 対話による具体化

1. 最初の説明と既存文書・会話から、確定事項、仮定、矛盾、未決事項を整理する。目的、対象ユーザー、利用場面、期待する振る舞い、Scope / Out of Scope、UI / UX、データ、状態遷移、エラー、権限、外部I/O、既存機能との関係、プラットフォーム制約、例外、受け入れ条件、完成条件を今回の要求に関係する範囲で点検する。
2. 設計やスコープへの影響が大きい不明点を優先し、原則1ラウンド2〜4問に絞って日本語で質問する。残りが1問なら1問でよく、確認観点を機械的にすべて質問しない。選択肢を示す場合は、具体的な挙動とトレードオフを添え、推奨案を決定済みとして扱わない。
3. 質問は今回の利用場面へ具体化する。「エラー処理はどうしますか？」ではなく、「録画開始時にカメラ権限が拒否されていたら、設定アプリへの誘導を表示しますか、それとも録画機能を非表示にしますか？」のように聞く。回答の矛盾や隠れた前提には、具体例や境界ケースを示して掘り下げる。
4. 回答を待ち、確定事項と未決事項を更新し、新たな不明点を再評価して次の質問を選ぶ。文書や会話で回答済みのことは繰り返さない。矛盾で再確認が必要な場合は、どの回答・仕様と衝突するかを示す。無回答を合意とみなさない。
5. 最初から十分具体的で矛盾のない仕様なら、形式的な追加質問は省いて確定内容の要約確認へ進む。

## 要件と設計の境界

決めるのは「何を実現するか」。class構成、Swiftファイル構成、architecture pattern、AVFoundation等の具体API、Package導入、Repository配置、詳細な内部アルゴリズムをこの工程で新たに決定しない。要件の実現可能性を確かめるため、既存architectureやplatform capabilityを調査してよい。調査結果は制約・実現可能性・未確認事項として共有し、実装方式の選定と区別する。既存の確定済み技術前提は`PROJECT_CONTEXT.md`に従う。

## 確定・保存の条件

次を満たすまで仕様を確定しない。

- 目的、Scope / Out of Scope、主要な振る舞いが明確。
- 重要な例外とエラー時の挙動が明確。
- 既存仕様との重大な矛盾がなく、意図した仕様変更は変更点と影響が合意されている。
- 設計やスコープを大きく左右する未決事項が残っていない。
- Acceptance Criteriaが条件・操作・観測可能な結果として検証でき、完成を判断できる。
- 残せる軽微な未決事項は内容、影響、後で判断できる理由を明示している。なければ「なし」とする。

main agentが目的、対象範囲と対象外、主要挙動と例外、受け入れ条件、残る未決事項、保存先を簡潔にまとめ、ユーザーの合意を確認する。既に会話で同じ内容の要約に合意済みなら重ねて承認を求めない。追加質問が不要でも、最初の説明をそのまま合意済み仕様とは扱わない。重要な未決事項や合意待ちがある場合は対話を継続し、確定保存や次工程への引き渡しを行わない。

## 合意後の保存

1. Initial Requirements Modeでは共通validationの保持・補完規則に従う。`absent + missing`のときだけassetを新規作成の土台にする。`present + missing`は不足セクション・項目だけ、`present + blank`は空欄・プレースホルダーだけを補う。既存ファイル全体をassetで置換しない。既存要件の変更は合意した箇所と整合に必要な関連箇所に限定し、その他の入力済み内容を保持する。
2. Feature Requirements Modeの新規仕様は`docs/ideas/YYYYMMDD-[feature-name].md`へ保存する。日付は作成日、feature nameは英小文字のkebab-case。既存仕様の更新では指定パスを保持し、同名の新規作成先が存在する場合は上書きせず対象を確認する。
3. custom agent `document_author`へ合意済みの内容と根拠、未決事項、保持する既存内容を渡し、対象1ファイルだけの作成・更新を委任する。所有パス、制約、出力形式、完了条件を明示し、同じコードベースに他の作業者がいること、他者の変更を戻さないことを伝える。main agentは対話と判断を担当し、文書作成の委任を省略しない。
4. 安定した要求が既存`docs/`へ影響する場合は更新候補と理由を仕様に記録する。このSkill内では永続文書を変更しない。
5. `document_author`の完了を待ち、結論、変更内容、根拠、検証結果、残課題を受け取る。main agentが最終diff、合意内容との一致、テンプレート残存、受け入れ条件、所有範囲外の変更を確認する。初期要件は同じ共通基準で再判定する。

## 停止条件

- 指定パスが`docs/ideas/`外、またはMarkdownでない。
- 更新対象の指定パスが存在しない。ただし、新規作成対象の`docs/ideas/initial-requirements.md`は除く。
- 初期要件の不足や永続文書の不足を解消せず追加仕様へ進もうとしている。モード選択に従って不足と次の工程を案内する。
- 必須情報・重要な未決事項・矛盾を解消できない、または確定内容への合意が得られていない。未確定の理由を示し、保存せず回答を待つ。
- `document_author`を使用できず、委任必須の文書作成を完了できない。

## 完了条件

- 選択したモードの確定・保存条件を満たし、合意済み内容が対象仕様に保存されている。
- 初期要件は共通判定で`valid`になっている。初回は「初期要件が固まったので、次は $setup-project で永続ドキュメントを作成できます」と案内する。セットアップ済みの初期要件更新では永続文書への影響を示し、再bootstrapを自動実行しない。
- 既存の初期要件を更新した場合、不足・空欄の補完とユーザーが合意した要件変更が反映され、それ以外の入力済み内容が保持されている。
- 追加仕様はテンプレートの必須論点を満たし、合意後に`confirmed`とする。「要件が固まったので、次は $prepare-steering で実装用steeringを作成できます」と保存パス付きで案内する。
- 既存仕様の更新では対象ファイルだけが変更されている。
- `.steering/`、永続文書、アプリコードを変更していない。
- `$setup-project`や`$prepare-steering`などの別Workflowを暗黙に開始していない。中間状態の案内だけで終了した場合は、仕様を新規作成・更新したとは報告しない。

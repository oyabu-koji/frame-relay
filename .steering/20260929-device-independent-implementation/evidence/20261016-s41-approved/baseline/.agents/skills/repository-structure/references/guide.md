# リポジトリ構造ガイド

## 設計原則

- プロジェクト規模と機能境界に合う最小構成にする。
- 変更理由が同じファイルを近くに置く。
- feature固有領域と複数featureで共有する領域を分ける。
- アーキテクチャの依存方向をディレクトリ規則として表現する。
- 現在の構造と将来の目標構造を混同しない。

## 記述項目

各ディレクトリについて次を定義する。

- 責務
- 配置するファイルと配置しないファイル
- 命名規則
- 外部へ公開する入口
- 許可する依存と禁止する依存
- 所属target・moduleとテストの配置

## Swift・SwiftUI・Xcode

- 実際のproject/workspace、target、App入口、画面遷移方式を確認する。未作成なら現状の不足と将来構造を分ける。
- Swiftソースは`.swift`とし、ファイル名は主な型や責務と対応させる。
- ディレクトリ、Xcodeでの表示、targetへの所属、Swiftモジュールを区別する。フォルダを分けるだけで依存が制御されるとは扱わない。
- iOSの端末APIや外部I/Oは設計されたサービス境界へ置く。
- Asset Catalog、ローカライズ等のリソースとテストは、ファイル配置に加えて所属target・参照方法を記述する。
- Xcodeの共有schemeや共有ビルド設定と、`xcuserdata`等の個人設定、DerivedData等の生成物を区別する。
- 用途説明やCapabilitiesは採用機能に必要なものだけ扱い、Info.plist等の独立ファイルが存在するとは決めつけない。
- 最初のプロジェクトは人間がXcodeでiOS App・SwiftUI・Swiftを選んで作成する。構造定義だけを理由にプロジェクト、外部生成ツール、空の`Package.swift`を追加しない。

## 依存ルールの例

```text
View -> 状態を所有する要素 -> 規則・計算
状態を所有する要素 -> サービス
共有領域 -X-> 特定機能の内部実装
規則・計算 -X-> SwiftUI / 端末API
```

実際に採用したアーキテクチャへ置き換え、機械的にこの例を固定しない。

## testと文書

- 採用した単体・統合・UIテストの配置とtargetへの所属を定義する。単体・統合は採用済みのSwift TestingまたはXCTest、UIはXCTestと対応させる。
- `docs/ideas/`を仕様、`.steering/`をタスク進捗、`docs/`を永続文書として区別する。
- `.agents/skills/`と`.codex/agents/`の役割を混同しない。

## 完成チェック

- ツリーに記載した主要パスの責務が説明されている。
- 命名例が特定機能へ偏っていない。
- 依存禁止がアーキテクチャ文書と一致している。
- テスト、リソース、docs、共有設定と個人設定の置き場所・所属が明確である。

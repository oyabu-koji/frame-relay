# アーキテクチャ設計ガイド

## 設計判断の書き方

各判断を次の順で記述する。

1. 対応する要件・品質特性
2. 採用する方式
3. 採用理由
4. 代替案と不採用理由
5. 制約・トレードオフ
6. 検証方法

「一般的だから」「最新だから」だけを理由にしない。

## 境界の例

- UI: SwiftUIによる画面描画、入力、アクセシビリティ。
- Application: ユースケース、状態遷移、非同期処理の調停。
- Domain: UIや端末APIへ依存しない規則と計算。
- Platform: iOSの端末機能、永続化、外部I/O。

プロジェクトに適合しないレイヤーを機械的に追加せず、採用した各境界について責務、公開インターフェース、依存方向、禁止事項を定義する。

## 品質特性

- 性能: 測定対象、目標、端末・データ条件。
- 信頼性: 失敗の隔離、再試行、フォールバック。
- セキュリティ: 入力、秘密情報、権限、ログ。
- プライバシー: 収集データ、保存場所、保持期間。
- アクセシビリティ: 操作、読み上げ、視認性。
- オフライン: 要件がある場合の機能範囲と同期方針。

## Swift・SwiftUI・iOS

- 採用するAPIが最低対応iOSと対象端末で使えるか確認し、利用可能条件と代替動作を示す。
- 状態の所有者、更新経路、共有範囲を定義する。特定の状態管理方式やMVVM等を一律に採用しない。
- UI更新と並行処理の境界、非同期処理の寿命・キャンセル、共有データの保護方針を定義する。
- 端末APIをUIへ直接結合せず、利用不可・拒否・失敗時の振る舞いを示す。
- 権限の用途説明、Capabilities、署名が必要な機能は要件と対応させ、不要な設定を要求しない。
- Xcode、Swift言語モード、最低対応iOSは`PROJECT_CONTEXT.md`の合意内容に従い、未決の値を決めつけない。
- 標準APIで満たせる範囲を確認し、外部依存・補助ツールを標準導入しない。採用が必要な場合だけ理由と制約を示す。

## テスト対応

- 規則・計算・状態遷移とサービス境界は、採用済みのSwift TestingまたはXCTestによる単体・統合テスト候補を示す。
- 主要な画面操作はXCTestによるUIテスト候補を示し、未作成のテスト構成は提案として区別する。
- 端末機能はSimulatorと実機で確認可能な範囲を分ける。
- 既存のproject/workspace、scheme、target、destination、test target・test planを確認した結果に基づき検証方針を定める。構成未作成時に実行可能なbuild/testを装わない。
- このSkillでは検証戦略を文書化する。Xcodeプロジェクト作成やビルド・テスト実行へ進まない。

## 完成チェック

- 技術判断がPRD・機能設計へ追跡できる。
- 責務と依存方向が明確で循環していない。
- 失敗時と端末差異の扱いがある。
- MVPに不要な仕組みを先回りして導入していない。
